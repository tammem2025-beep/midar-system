# مراجعة تنافسية وخارطة تطوير M

**تاريخ المراجعة:** 25 أكتوبر 2026  
**النطاق:** مراجعة مرجعية مركزة للمنتجات الرسمية المختارة وموصلات المنصات، وليست ادعاءً بفحص كل موقع أو كل تطبيق موجود.  
**النسخة:** نفس خط المشروع الحالي؛ لا يتطلب هذا المستند إصدارًا جديدًا.

## 1. المراجع السوقية وما الذي نتعلمه منها

| المنتج | نقاط القوة الظاهرة في المصادر الرسمية | ما ينبغي أن نستفيد منه في M |
|---|---|---|
| [Buffer](https://buffer.com/) | تخطيط ونشر المحتوى، تقويم بفلاتر وطرق عرض، مساعد للكتابة، Insights، تعاون مجتمعي | تقويم واحد بفلاتر المنصة والحالة، حفظ المسودات، معاينة واضحة، وقياس النتائج بعد نشر فعلي |
| [Hootsuite](https://www.hootsuite.com/platform) | جدولة ونشر، أدوات كتابة مدعومة بالذكاء الاصطناعي، موافقات الفريق، تحليلات ومقارنة منافسين، صندوق رسائل موحد | تحويل الرسائل والمهام والموافقات إلى سير عمل متصل، وإظهار ما هو مدعوم فعلًا لكل منصة |
| [Metricool](https://metricool.com/planner/) | تخطيط متعدد المنصات، معاينة التنسيق، تحرير حسب الشبكة، Reels والفيديو، أدوات AI، تعاون وتقارير | استوديو محتوى بمقاسات معاينة مناسبة، تخصيص المنشور لكل قناة، فلاتر واضحة، وتجهيز التحليلات قبل بناء توصيات النشر |
| [Sprout Social](https://support.sproutsocial.com/hc/en-us/articles/360051650231-Standard-Plan) | Smart Inbox، تقويم نشر، جدولة ومسودات وقوائم انتظار، تقارير، تطبيقات هاتف وفريق | صندوق رسائل يعتمد Webhooks حقيقية، إسناد المحادثات للأعضاء، وسجل حالة من الوارد حتى الحل |

هذه المقارنة تستند إلى صفحات الشركات ووثائق الدعم الرسمية؛ الميزات الفعلية تتغير حسب الباقة والمنصة والصلاحيات.

## 2. حالة M الحالية كما تظهر في المصدر

- **قاعدة جيدة موجودة:** لوحة تحكم، إدارة محتوى وتقويم داخلي، مكتبة وسائط، استوديو فيديو قصير، حملات، عملاء ومهام، فريق وصلاحيات، وسجل نشاط.
- **Facebook وInstagram:** موصل Meta حقيقي لربط حسابات مؤهلة وقراءة محتوى تسمح به الصلاحيات، بما في ذلك Reels متى أعادتها واجهة API. هذه الدفعة حسّنت عرض الحالة والفلاتر، لكنها لا تفعّل النشر التلقائي.
- **Telegram:** موصل جزئي للتحقق من الوجهة ونشر النص يدويًا بعد الإعداد؛ ليس صندوق رسائل كاملًا ولا مجدولًا خلفيًا عامًا.
- **WhatsApp وX وYouTube وTikTok وLinkedIn:** لا ينبغي إظهار هذه القنوات على أنها متصلة أو جاهزة للنشر قبل تنفيذ OAuth/API أو Webhooks والتحقق من الحساب.
- **تسجيل Google:** يخص الدخول إلى M؛ لا يعطي تلقائيًا إذنًا لإدارة خدمات Google أو حسابات السوشيال.
- **الهاتف:** الواجهة متجاوبة وPWA؛ لا يوجد في المستودع حاليًا ملف APK أو IPA أصلي. التثبيت العام والوصول من الخارج يحتاجان خدمة مستضافة بعنوان HTTPS وقاعدة بيانات دائمة.

## 3. ترتيب الأولويات المقترح

### P0 — تثبيت تشغيل النسخة الحالية
1. اجتياز اختبارات Python وJavaScript وPlaywright وبناء Windows بعد كل تغيير.
2. توزيع حزمة Windows المحمولة الاختيارية مع فصل مجلد بياناتها عن بيانات المثبت العادي.
3. تفريغ الواجهة من حالة اتصال مبهمة، وتوضيح خطأ OAuth أو الصلاحيات بدل عرض محتوى تجريبي.
4. اختبار أول تشغيل، التحديث، عدم ضياع البيانات، والنسخ الاحتياطي والاستعادة.

### P1 — النشر الرسمي والجدولة
1. تنفيذ موصل مستقل لكل مزود، ببوابة capabilities تحدد بدقة القراءة/النشر/الوسائط/التعليقات.
2. حفظ المنشور مع وقت UTC ومنطقة مساحة العمل، ثم تشغيل عامل خلفي مستمر مع إعادة محاولة محدودة ومفتاح idempotency.
3. تتبع الحالات: جاهز، بانتظار الموافقة، مجدول، قيد الإرسال، تم النشر، فشل، أو نتيجة غير مؤكدة.
4. عدم إعادة المحاولة العمياء بعد timeout؛ يجب التحقق من حالة المزود لتجنب منشورات مكررة.

### P1 — صندوق رسائل موحد
1. استقبال Webhooks الرسمية وتخزين معرفات الرسائل الخارجية ومعلومات الوقت والمصدر.
2. توحيد عرض المحادثات مع الحفاظ على قواعد كل منصة، وإسنادها إلى عضو، ووسوم، ردود محفوظة، ووقت استجابة.
3. تفعيل الإرسال من خادم آمن فقط بعد التفويض والصلاحيات، وعدم محاكاة الرسائل الخارجية داخل سجلات محلية.

### P2 — تحليلات وأدوات AI نافعة
1. جمع مؤشرات الأداء التي تسمح بها المنصة، مع بيان مصدر البيانات والفترة الزمنية.
2. مساعد محتوى يستخدم مزود نموذج محددًا ومهيأً في الخادم؛ يشمل صياغة عربية، بدائل للنبرة، أفكارًا، وملخصًا لكل شبكة.
3. طلب مراجعة بشرية قبل النشر، وتوضيح المحتوى المولد أو المعدل، وحماية أسرار العملاء وعدم إرسالها إلى مزود AI بلا إعداد واعٍ.
4. بناء توصيات أفضل وقت للنشر فقط بعد امتلاك بيانات نشاط كافية لكل قناة؛ لا تُعرض أرقام أو تنبؤات مختلقة.

### P2 — الاستعداد كخدمة SaaS
1. عزل بيانات المستأجرين واختبارات تفويض لكل endpoint، ومراجعة انتهاء/تدوير الرموز.
2. مراقبة الأخطاء ومقاييس الطوابير وسجل تدقيق للربط والنشر.
3. نسخ احتياطية مجدولة واختبار استعادة فعلي، وبيئة staging منفصلة عن بيانات المستخدم.
4. استضافة HTTPS وقاعدة بيانات دائمة وسياسة أسرار، وخطة ترحيلات قابلة للتراجع.

## 4. كيف نستفيد من أدوات تطوير الذكاء الاصطناعي دون الاعتماد الأعمى عليها

- [OpenAI Codex](https://openai.com/index/codex-for-almost-everything/)، و[GitHub Copilot coding agents](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task)، و[Cursor Agent](https://prod.cursor.com/help/ai-features/agent) أمثلة على سير عمل يقرأ قاعدة الشيفرة، يعدل ملفات متعددة، ويستخدم الاختبارات أو مراجعة التغييرات. الدرس لـ M هو أن كل تغيير يجب أن يكون محددًا وقابلًا للاختبار ومراجعًا، لا أن تُدمج شيفرة مولدة دون CI.
- ينبغي أن يكون المساعد داخل M متصلًا بمزود AI معلن ومهيأ بمفتاح خادم؛ لا تُضمّن المفاتيح في الواجهة ولا تعتبر استدعاء نموذج بديلًا عن صلاحيات API أو موافقات المنصات.
- تستخدم عمليات البناء والاختبار بيانات وهمية، وأي أسرار OAuth أو قواعد بيانات حقيقية تبقى خارج Git.
